Deep Technical Dossier

Why the Servant FX still do not render

This document consolidates the BO3 Rev Servant port into one place: current architecture, the exact failure timeline, the bridge experiments that were disproven, the surviving constraints, and the current model of the rendering gap. It is written to be a restart point for engineering, not just a narrative archive.

Tutorial

Use this section if you are re-entering the project cold and need to understand the current Servant lane before changing code.

1. Understand the target

The target is not "make BO2 behave like T5." The real target is:

  • T7 for the Servant's content, look, and intended behavior.
  • T6 for the engine contract, runtime semantics, client/server split, and script API.
  • T5 only as a conceptual reference when T6 lacks an obvious analogue.

2. Understand the split

The project separated into three lanes:

  • Shell lane: get a BO2 donor weapon accepted and playable.
  • Model/material lane: get BO3 geometry and materials stable inside T6.
  • Presentation lane: get BO3-style FX and animations visibly playing.

3. Understand the current win state

  • The donor shell works.
  • The custom model path works.
  • The gameplay logic works.
  • The BO3 raw FX assets link.
  • The remaining blocker is presentation: effects still do not render visibly in-game.

4. Understand the current failure

The strongest current model is:

  • the server creates bridge entities and calls the bridge path
  • the clientscript override loads and initializes
  • the client still never reaches the BO3 playback threads
  • therefore the gap is in client discovery/dispatch, not basic FX asset linkage

How-to

Use this section as the operational runbook for continuing the Servant FX lane.

Build and deploy

  1. Run python _build/run_bo3_rev_probe_case.py mg08_v2_bo3_weapon_only_rawfx_safeimg.
  2. Confirm the archived report in _build/bo3_rev_probe_cases/mg08_v2_bo3_weapon_only_rawfx_safeimg/.
  3. Restart Plutonium completely before testing a new survival FF.
  4. Confirm the first runtime log line contains the expected build_tag.

What to look for in logs

  • Server init: [bo3_rev][start] stage=init ... raw_fx=1 ... client_fx=1
  • Server bridge: projectile_equipment_bridge and vortex_equipment_bridge
  • Client init: [bo3_rev][csc] zm_transit main ..., register_client_fields, init build=...
  • Desired next signal: [bo3_rev][csc] discovered ... or equipment bridge ...
Current test criterion
The next meaningful success is not "the vortex looks perfect." It is "the client logs prove it discovered or dispatched a bridge entity and entered a BO3 FX playback thread."

Explanation

This section explains the project's logic, not just its steps. It captures what each failure proved and why the current rendering gap is narrower than it first appears.

Timeline of major issues and findings

Fresh-name Servant identity failed

Early lane - before donor-shell pivot

Attempts to register a true apothicon_servant_zm identity succeeded at the registration layer but still failed engine queries. The decisive runtime symptom was undefined clip/max data and failed give paths.

What it proved: weapon identity was blocked in the normal mod lane. The project had to pivot to donor shells.

ray_gun_zm proved to be a bad donor

Donor isolation phase

The Ray Gun shell could take override values, but it repeatedly crashed on first-person DObj composition even with tiny or stock replacement models.

What it proved: the crash was not simply "too many BO3 bones." The Ray Gun shell has hidden first-person baggage.

mg08_zm became the working donor shell

Shell stabilization

The project moved through simpler shells and landed on mg08_zm as the live carrier. This shell proved structurally compatible with the reduced BO3-derived weapon rig and gave the right silhouette for a heavy wonder weapon.

Material/IPAK contract problems were fixed

Model/material lane

The weapon progressed from invisible to chrome to materially usable. The major breakthrough here was recognizing that image-backed BO3 surfaces required a correct runtime IPAK contract, not just staged material JSON.

The raw BO3 FX importer became real

Raw FX lane

Local OAT work in LoaderFxT6.cpp made the raw BO3 Servant graph parsable and linkable into T6 FxEffectDef assets. At this point the problem stopped being "can we import BO3 FX?"

Loose fxt_* image overrides were poisoning runtime behavior

Build 0313234021_485c81

Old loose FX images in AppData were removed. After cleanup, visible debug lightning started to appear again. This proved the runtime was sensitive to global FX image contamination.

Server-side FX playback alone was not enough

Builds 031400* through 031405*

Many builds proved that BO3 FX names loaded and server-side playback calls fired, but the visible BO3 projectile/vortex still did not appear. This pushed the investigation into the server/client presentation model.

T5-style bridge assumptions were disproven

Builds 0316045334_485c81 to 0316211302_485c81

Two guessed bridge primitives were rejected by BO2 directly:

  • setclientfield(...) unresolved in raw/server GSC
  • register_clientflag_callback(...) unresolved in T6 CSC

What it proved: the correct implementation must be T6-native, not T5-shaped.

Transit CSC override path was validated

Builds 0316213551_485c81 onward

The client override clientscripts/mp/zm_transit.csc and dedicated Servant FX script both loaded successfully from the fastfile. That removed an earlier ambiguity about whether our clientscript lane was even active.

Stock equipment bridge still did not dispatch

Build 0317004838_485c81

The server successfully created anchors and invoked the BO2 stock equipment bridge, but the client never printed a single equipment bridge callback line. This narrowed the problem to client dispatch or discovery.

Current phase: explicit client discovery fallback

Build 0317011234_485c81

The newest pass no longer trusts the stock equipment callback alone. It also scans for replicated anchor models directly on the client.

Current thesis: the remaining render blocker is the bridge entity being visible to the server path but not entering a client-visible dispatch surface.

Current architecture

Server half

  • mod_i_am_mod.gsc.in owns the donor shell, fire watcher, projectile spawn, and vortex logic.
  • It creates a replicated FX anchor entity for projectile and vortex visuals.
  • It attempts to signal BO2's stock equipment bridge via maps\mp\zombies\_zm_equipment::signal_equipment_activated().
  • It also tags anchors with targetname, script_noteworthy, and script_string.

Client half

  • zm_transit.csc.in initializes the Servant client FX script during the Transit clientfield registration window.
  • _bo3_rev_servant_fx.csc.in loads imported BO3 FX assets locally.
  • It registers a stock equipment callback override keyed by model string.
  • It also now runs a model-discovery loop as a fallback path.

The current rendering gap

Current best model
The engine is no longer failing at BO3 raw FX linkage. It is failing at the boundary between replicated bridge entities and client-visible dispatch. The BO3 FX are loaded; the client playback threads are not being entered.

What we know with high confidence

  • The raw BO3 Servant FX names link and loadfx() successfully.
  • The Transit client override is live.
  • The dedicated Servant client FX script is live.
  • The server now creates bridge entities successfully.
  • The server now reaches the equipment bridge path successfully.
  • The client still does not log bridge callback entry.

Most likely remaining mismatches

  1. The chosen stock bridge surface still expects a different entity archetype than our anchor.
  2. The bridge marker model or hidden-state choice prevents client dispatch or discovery.
  3. The replicated anchor exists server-side but is not client-visible in the way _zm_equipment.csc expects.
  4. The stock equipment bridge is simply the wrong bridge surface for arbitrary Servant anchors, and a different T6-native clientfield path should be reused instead.

How far we are from visible BO3 FX

We are no longer "far" in the sense of having multiple unsolved systems. The gap is narrower:

  • Shell/gameplay: good enough
  • Model/material: good enough to keep iterating
  • Raw FX import: good enough
  • Server-to-client presentation bridge: still the hard blocker

The project is one bridge-layer away from a meaningful BO3 FX render test.

Next steps

This is the recommended order from the current evidence, not a generic roadmap.

  1. Run and inspect 0317011234_485c81 specifically for model-discovery logs.
  2. If discovery logs appear but there are still no visuals, move focus to local client playback and imported FX fidelity.
  3. If discovery logs still do not appear, stop using the equipment bridge as the primary assumption and switch to a stock T6 clientfield path that is known to target an entity class we can reliably spawn and replicate.
  4. Only after the bridge is proven alive should the project resume larger BO3 vortex fidelity work.
  5. Keep the animation lane separate until the FX bridge is solved.

What should not be retried blindly

  • Raw/source setclientfield(...) bridges
  • T5-style clientflag callback registration in CSC
  • Large BO3 FX graph changes before the client bridge proves it can enter playback threads

What remains genuinely promising

  • T6-native, mod-only bridge surfaces
  • Client discovery off replicated marker entities
  • BO3 raw FX import through the patched OAT T6 loader
  • The current donor/model/gameplay foundation
